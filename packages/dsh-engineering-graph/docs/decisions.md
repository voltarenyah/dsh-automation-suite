- **决定**：`knowledge_network` 的默认 `view` 从 `logic` 切换到 `ladder`，唯一门槛是第 7 阶段的指标（条件题、写入者题、时序题、冲突题的正确率，以及 token 开销）。

## LAD-03 · 阶段 2 的线圈位置与取反规则：撤回保守默认 ✅

- **日期**：2026-11-27（M0 首轮），同日增补
- **依据**：[`docs/research/tia-lad-structure-rules.md`](../../../docs/research/tia-lad-structure-rules.md) 第 7、8.3 节。
- **结论**（TIA V17 实测，均合法且导入后无相关告警）：
  - 普通线圈（`Coil`）后面可以继续接元素（E1）。
  - 置位/复位线圈（`RCoil`）位于分支中间、后接元素（E5）。
  - 嵌套分支不限层数（E2）。
  - 扇出：一条 Wire 挂多个目标（E4）。
  - 取反触点（`Negated`）串联与分支内（E6）。
  - 同一网络内同一位 S 与 R 双写，前提是各用独立 Access（E3a'）；跨网络双写合法（E3b）。
- **因此**：阶段 2 **不得**据上述元素标 `unstructured`。
- **未覆盖**：盒指令（`Move`、比较、`TON` 等）位于分支中间；O 盒合流之后接元素。这两项在 E7、E8 之前**不下结论**，阶段 2 对其默认标为 `unstructured`，原因 `box-in-branch-untested` 或 `merge-untested`。
- **E7、E8 不做**（2026-11-27 用户决定，M0 到此收尾）。因此：
  - "盒指令位于分支中间" 与 "O 盒合流后接元素" **永久保持未验证**。
  - 阶段 2 对含盒指令或被合流的网络标 `unstructured`，原因 `box-in-branch-untested` / `merge-untested`。
  - Step 6 第 4 轮的失败原因**不追查**，因为它已不影响读侧：读侧不需要知道 TIA 接受什么，只需要正确还原已有网络的连线。
- **影响评估**：M0 结论足以覆盖布尔元素（触点、线圈、置位/复位线圈、取反、扇出、嵌套分支、同位双写），这些占语料的绝大多数（见 `docs/research/lad-corpus-inventory.md`）。盒指令网络仍可读，只是不做串并联归约。

## LAD-11 · 阶梯视图的两道守卫：库存断言 + 真实端到端 ✅

- **日期**：2026-11-27
- **问题**：阶梯视图有三段链路（C# 计算 → 属性入库 → TS 查询与渲染），而当时每段各有一个测试，**没有任何测试证明三段是接上的**。属性名在任一侧改一个字母，所有既有测试仍然全绿，模型只会静默拿到语句文本。
- **守卫 1（引擎自检，DB 级）**：ingest 之后直接查 `graph_node_properties`，断言"有 LAD 网络却没有任何 `ladderText`"会失败。实测 `4058/4142`，并把这 84 条差额解释写进输出（无 FlgNet 源、或无线圈且无开路端），避免被误读为漏存。
- **守卫 2（TS，真实引擎）**：`test/16-ladder-end-to-end.test.mjs` 写一个两网络 LAD 块 → 真实引擎 ingest → 查属性 → 用真实工具跑 `view='ladder'` 与默认视图。它同时钉住三件事：并联的两条路径确实各占一行、OR 盒不出现在条件里、默认视图仍是 `logic`。
- **为什么值得两道**：守卫 1 看不到"工具取错列"，守卫 2 看不到全库范围；两者互补。

## LAD-09 · 读法指南进包内文档 + 工具描述，不进 skills/ ✅

- **日期**：2026-11-27 · 阶段 6
- **背景**：计划原本要把 `LAD-READING.md` 放进 `skills/tia-openness/`，并在路由 `SKILL.md` 加一行引用。
- **决定**：改为包内 `docs/LAD-READING.md` + 把浓缩版写进 `knowledge_network` 的工具描述。
- **理由**：
  1. 路由 `SKILL.md` 已 8114 字符，上限 8192，加引用会超限（`skills:check` 会拦）。
  2. 根 `AGENTS.md` 与 tia-openness 包的约定都写明：**运行时模型真正看得见的是工具描述与 skill 目录**，而工具描述常驻可见、无需加载。读法指南的第一读者正是要调用 `knowledge_network` 的模型。
  3. 读法指南讲的是 `knowledge_*` 工具（属于本包），不是 Openness API，放在 tia-openness 的技能库里反而错位。
- **代价**：模型不会"按需加载长文"，只能看到工具描述里的浓缩版；长文（五个角度、常见误判）需要人或子 agent 主动读文件。

## LAD-10 · 评测题库从数据库生成，并排除两类不可判分的题 ✅

- **日期**：2026-11-27 · 阶段 7 准备
- **决定**：题库由 `scripts/eval/lad-qa/generate.ps1` 从知识库生成，真值取 `ladderText` 与读写边，不手写。
- **两条数据质量规则**：
  1. **排除含不透明步骤的网络**：`[Move]`、`[Eq]`、`[Call]` 的条件在别的网络里，用字符串真值判分会把"正确但无法表达"当成"错误"。
  2. **排除备选超过 6 条的线圈**：那是阅读量测试，不是理解测试。
- **顺带修的渲染问题**：盒指令步骤原来渲染成裸名字（`A AND Eq AND B`），看起来像一个条件项。现改为方括号（`[Eq]`），既提示不透明，也让题库可以自动识别并排除。
- **未完成**：实际跑分需要在装有本插件的会话里进行；当前会话的 profile 没有加载它。

## LAD-08 · 阶梯视图存节点属性，不建 flg_* 表 ✅

- **日期**：2026-11-27 · 阶段 4
- **决定**：归约出的阶梯文本由 C# 渲染（`LadderText`），作为 network 的节点属性 `ladderText` 入库；TS 的 `knowledge_network(view='ladder')` 通过 `graph_node_properties` 子查询读取。
- **为什么不建表**：阶段 5 计划里的 `flg_elements`/`flg_wires`/`flg_rung_nodes` 是为"按结构查询"（谁喂这个引脚、这个元素在哪个分支）准备的。当前阶段真正被消费的是"一个网络的可读结构"，属性足以支撑，且**旧库自动降级**（缺属性 → 回退到语句文本并说明），不需要重建库。
- **代价**：跨网络的结构查询（例如"所有写这个位的元素及其祖先条件"）暂时做不到，仍需 `knowledge_network` 逐个网络读。若阶段 5/7 证明这是瓶颈，再补表；届时 `ladderText` 可保留为冗余视图。
- **格式**：每条路径一行，"若干行同一线圈"表示或（OR）：
  ```
    (S) G.%X2   <-  Disable_VocDoorFunction
    (S) G.%X2   <-  Mvt_VocDoor_DN.FullOpen AND NOT Manu_Loading
    -- (no coil)   <-  Starting_Value.CPU_Cycle_Time_Enable AND Runtime
  ```
  不用 ASCII 梯形图：本工程有 34 个触点串联的网络（`030_Faults_Cav_A`），列对齐的图会崩，而模型读文本比读图更稳。

## LAD-07 · 等价校验抓到两个真 bug：字面量 TRUE/FALSE 与取反线圈 ✅

- **日期**：2026-11-27 · 阶段 3
- **背景**：用"路径表达式 vs `logicStatements`"在 reference 工程全量比对，首轮 9 处分歧、次轮 2 处、最终 0 处。
- **bug 1：字面量 `TRUE`/`FALSE` 被当成自由变量。** 真实网络用 `AND false` 作占位条件（如 `128_Unload_Cured_Tyre_Standard` 网络 29 的 `(G.%X8 AND NOT I_Jib_In) AND false`），若把它当变量，两个语义等价的表达式会随机地"不一致"。修法：`BooleanExpression.OperandTerm` 把 `TRUE`/`FALSE` 识别为常量。
- **bug 2：取反线圈的写入值等于条件取反。** `030_Faults_Cav_A/B` 网络 1 是 34 个取反触点串联后接一个**取反线圈**（`<Part Name="Coil"><Negated Name="operand"/></Part>`），翻译器给的是 `NOT(AND 链)`，正确；归约原来把线圈排除在条件外且忽略其取反，结论相反。修法：`RungCoil.Negated` + `RungModel.ValueExpression`。
- **教训**：这两个 bug 都不会让任何"能跑通"的检查失败——元素数、线数、语句数全都正常。只有把两条独立实现对同一网络求值才暴露。这正是阶段 3 存在的理由。
- **验收**：reference 工程 `coils=1323` 全部一致（`networks=4058`，跳过 `box=2306`、`statements=14`、`unresolved=589`，抽样 36）。

## LAD-06 · 归约用"电源轨到终端的路径"，不建串并联树 ✅

- **日期**：2026-11-27 · 阶段 2
- **背景**：计划原本写的是把网络归约成 `Series`/`Parallel` 树。实际 LAD 拓扑不是树：扇出会让多个独立 rung 共享一个前缀，O 盒合流会让多条链回到同一个分叉点。建树要从每个合流点反向找分叉点，找不到就只能猜。
- **决定**：改为从电源轨出发**枚举到终端的完整路径**。每条路径是一个步骤序列，路径与其终点的对应关系即语义：
  - 一个线圈有多条路径 = 这些路径相或（OR）；
  - 一条路径的多个步骤 = 这些条件相与（AND）；
  - 扇出与嵌套分支自动表现为多条路径，无需专门规则。
- **明确不进入条件的两类元素**：OR 盒（结构算子，其作用已体现为多条路径）与线圈（写入 RLO 并原样传递，M0/E1、E5 实测允许其后再接元素）。
- **与阶段 4 的关系**：阶梯图渲染可由路径按共享前缀合并得到，因此不建树不损失信息；若后续需要显式树，再在路径之上派生，而不是回头改归约。
- **验收**：reference 工程 4058 个网络全部归约为 structured（0 个放弃），得到 3994 个线圈；pilot 与样例同样 0 放弃。

## LAD-04 · 元素图的两条语义：OpenCon 不是元素引用，Call 引脚方向来自声明 ✅

- **日期**：2026-11-27 · 阶段 1 实现中由真实导出发现
- **背景**：按名字表推断引脚方向、把 `OpenCon/@UId` 当元素引用，在 reference 工程的 4058 个 LAD 网络里产生了 20 处误报（`flg_no_source`）。两处都是**规则本身错**，不是数据脏。
- **结论 1：`<OpenCon UId="x"/>` 的 UId 是开路端点自身的标识，不是任何元素的引用。**
  典型形态：`<Wire><OpenCon UId="40"/><NameCon UId="32" Name="DelayTimer_Msec"/></Wire>`——该分支不通向任何目标。
  因此这类线记为 `FlgWire.IsOpen = true`，**不**做 UId 存在性校验、**不**报错。
- **结论 2：`<Call>` 的引脚方向必须读 `<CallInfo><Parameter Name="…" Section="Input|Output|InOut|Return"/>`，不能靠名字猜。**
  反例：`FaultCode` 是 `Output`，但按名字表既不像输入也不像输出，会被当成输入，导致整条线与方向判断颠倒。
  `Section` 到角色的映射：`Output`/`Return` → 输出，`Input`/`InOut` → 输入（`InOut` 的读写双性留给阶段 5 记录）。
- **结论 3：`<Instance>` 是独立的引脚宿主，必须作为元素。**
  同一调用的 `en` 落在 `<Call>` 上，而 `in` 落在 `<Instance>` 上（实测 `200_Outputs_PC`，Wire 43 引用 Instance UId 的 `in` 引脚）。若只登记 Call，这类线会全部悬空。
- **验收**：修复后 reference 工程 `4058` 个网络、`58340` 个元素、`61487` 条线、`2775` 个取反引脚，零诊断；`negated=2775` 与语料普查（`docs/research/lad-corpus-inventory.md`）逐字吻合。
- **对后续阶段的约束**：阶段 2 的归约、阶段 4 的梯级渲染都必须经由 `FlgNetworkGraph.RoleOf`（先声明、后名字表），不得直接调用名字表。
