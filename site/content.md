### FAQ
1. **Is this an official DeepSeek or Siemens product?**
   No. It is an unofficial DeepSeek Harness distribution plus our own TIA and engineering plugins. DeepSeek, Siemens and TIA Portal are named for reference only; the MIT license covers this repository, and TIA Portal / PLCSIM licensing stays with you.
2. **What do I need to run it?**
   Windows 10/11 x64 and DeepSeek Harness — the desktop setup fetches DSH if it is missing. The TIA tools need TIA Portal V17 with Openness, simulation needs PLCSIM Advanced with API 4.0, and the knowledge graph needs .NET 8.
3. **Does it write into my project on its own?**
   No. Reads are explicit calls; writes are tool calls with dry-run where it matters, run inside a TIA transaction and read back before they are reported as done. If verification fails, the transaction rolls back and the project is left as it was.
4. **How are changes versioned?**
   The project source is exported to text and committed to Git. The Versions panel reads the last commits, lists per-block changes and their kind — interface, code, comments, properties — so a change is reviewable instead of a binary blob.
5. **Does it need the cloud?**
   It runs locally: shell, plugins and the TIA controller are all on your machine. The only outbound traffic is the model API you configure, plus GitHub and download.deepseek.com while installing.
6. **What is not there yet?**
   V18 support, hardware configuration, online & download, block comparison and cable/terminal drawings. The Roadmap page gives the honest status of each.

## Architecture

### Page head
- Eyebrow: Architecture
- Title: One distribution, twelve bundles
- Lead: The suite is a DeepSeek Harness profile over twelve independently installable bundles. The profile decides which packages compose, which services connect them, and which tools each preset can see.

### Why a distribution
Note: DSH installs bundles; the profile composes them and sets policy.

1. **Bundle = capability** — Each plugin is a normal DSH bundle with its own `cordis.patch.yml`. It can be installed on its own; the release publishes one tarball per package.
2. **Profile = composition** — A profile is the composition layer: it declares bundles, presets and policy. It is not a bundle: `dsh plugin add` rejects it as `not-a-bundle`.
3. **Release = a tested combination** — The GitHub release ships the blueprint, per-package tarball URLs and an installer. It pins the combination that was verified together — not a mega-package.

### Principles
Note: Four rules that decide how the pieces are assembled.

1. **Compose, don't absorb** — One capability per bundle. The distribution is a profile over packages, not a single plugin that swallows them.
2. **Services are the cross-plugin API** — Plugins never import each other. They meet through a small set of host services — TIA access, the knowledge graph, and the git repository — and report a missing service instead of guessing.
3. **Visibility is a preset decision** — Host rows own processes and services. Tool rows are mounted by a preset, so the same package can expose different surfaces to leader, auditor and expert.
4. **Policy is configuration** — Personae, the default preset, disabled built-ins and subagent limits live in the profile. Changing them does not rebuild a plugin.

A preset mounts an entry point:

```yaml
# profile/cordis.patch.yml — a preset mounts an entry point
- id: leader-tia-tools
  name: '@voltarenyah/dsh-tia-openness-v17-min/tools'

# the host row is separate; it owns the controller and the service
- id: tia-openness-v17-min
  name: '@voltarenyah/dsh-tia-openness-v17-min'
```

Note: `leader` gets the working surface; `auditor` owns the version workflow; `expert` gets read-only drill-down. A subagent cannot inherit a tool its preset did not mount.

### How it runs
Note: One process boundary, because Openness demands it.

Openness can only be called from a 64-bit .NET Framework process, so the TIA plugin owns a C# controller subprocess and speaks one JSON object per line over stdio. Requests are serialized; a timeout terminates and restarts the controller.

`TiaOpennessV17Min.Controller.exe · x64 · .NET Framework 4.8`

### Maturity
Note: The three layers, as they actually are.

1. **Access** — Partial
   Block export and import, compile and project data work on real projects. Twenty operations added in v0.2 are still unverified in the field.
2. **Semantics** — Prototype
   XML to SQLite graph works on fixtures. Freshness, incremental updates and a compatibility layer are not done.
3. **Governance** — Partial
   The Git tools are general-purpose. The version workflow is two steps: sync the source tree, then commit it.

### Compatibility
Note: What it runs on today.

- Operating system: Windows for the TIA tools. Other platforms can load the plugins, but TIA calls fail.
- DeepSeek Harness: Any version that can load bundles; built and tested against 0.2.1-rc.2.
- TIA Portal: V17 only — V16 and V18 are not compatible.
- Node.js: 22.19 or newer.
- Openness: Siemens.Engineering.dll from Portal V17, and membership in the local “Siemens TIA Openness” group.

## Get Started

### Page head
- Eyebrow: Get started
- Title: Install it, start it, verify it
- Lead: One setup for most people: the desktop app. Three alternates for special cases — the release zip, the repository starter, or a single bundle. All run the same blueprint in an isolated DSH_HOME.

### Before you start
Note: The suite runs on DSH. The desktop setup installs what is missing; only the TIA and PLCSIM tools need Siemens software.

| Requirement | What it needs |
| --- | --- |
| Operating system | Windows 10/11 x64 for the desktop shell and all TIA/PLCSIM work. The non-TIA plugins can load on other platforms, but this guide assumes Windows. |
| DeepSeek Harness | The desktop setup reuses an installed DSH (≥ 0.2.1-rc.1; verified against 0.2.1-rc.2) and downloads the official runtime when it is missing. The zip and single-bundle paths expect it preinstalled. |
| TIA Portal V17 | Only for the TIA tools: V17 with Openness — V16 and V18 are not compatible; TIA also brings the .NET Framework 4.8 runtime the controllers use. Requires `Siemens.Engineering.dll` under `PublicAPI\V17` and the current user in the local “Siemens TIA Openness” group. |
| PLCSIM Advanced | Optional; only for the simulation tools. Needs PLCSIM Advanced with API 4.0 (4.0–7.0 runtimes work). |
| Git CLI | Only for the git tools. DSH does not bundle git; run `git --version`, or install Git for Windows. |

Note: Excel and PDF support is pure JavaScript/WASM — no Microsoft Office or Acrobat install. The only desktop software this suite calls is TIA Portal, PLCSIM Advanced and Git.

### Install the desktop app
Note: Recommended since 0.2.3: one setup exe, per-user, no Node, no console window. The wizard installs the WebView2 shell, a pre-built profile and the doctor, and downloads DeepSeek Harness and WebView2 first if either is missing.

1. **Run the setup** — image `assets/images/desktop/setup-1-smartscreen.png` (SmartScreen before “More info”)
   Download `dsh-automation-suite-setup-<version>.exe` from Releases and run it. The binary is not code-signed, so Windows stops it once with the SmartScreen dialog — “Unknown publisher” is expected here, not a sign of tampering.
2. **Allow it through SmartScreen** — image `assets/images/desktop/setup-2-smartscreen-more-info.png`
   Click More info, check that the app is `dsh-automation-suite-setup-<version>.exe` with publisher “Unknown publisher”, then click Run anyway. If you want certainty first, compare the published SHA-256 with `Get-FileHash`.
3. **Welcome page** — image `assets/images/desktop/setup-3-welcome.png`
   The wizard names the version it is about to install and asks you to close other applications. Nothing has been written yet; the close button leaves the machine untouched.
4. **Destination folder** — image `assets/images/desktop/setup-4-destination.png`
   The default is `%LOCALAPPDATA%\dsh-automation-suite` — per-user, no administrator rights, removable through Windows Settings. The profile ships with its `node_modules` already materialized, so setup needs about 218 MB; the stable shell, the versioned app layer, `install.json` and the uninstaller all live here.
5. **Additional tasks** — image `assets/images/desktop/setup-5-tasks.png`
   A desktop shortcut is the only optional task; the Start-menu entry is always created. Next starts the copy. If DSH or WebView2 is missing, the wizard then runs a PowerShell step that downloads the official package (DSH is about 300 MB) and verifies its SHA-512 and DeepSeek signature before installing it — that is the only part that needs a network. Afterwards it copies the fixed profile into `dsh-automation-suite-home`, merges any older overrides and runs `doctor`.
6. **Finish and launch** — image `assets/images/desktop/setup-6-finish.png`
   Leave Launch DSH Automation Suite checked and click Finish. The app window opens with the suite profile already active — there is no console window to keep open.
7. **What opens** — images `assets/images/desktop/app-light-en.webp` (light, EN) plus `app-dark-en.webp` and `app-dark-zh.webp`
   A WebView2 window with the same 40 px title bar as the DeepSeek Harness desktop app — Application and Edit menus on the left, window buttons on the right, the suite preset and its five right-hand tabs already loaded. There is no address bar and the shell never depends on your browser; theme and language follow the app's own settings.
8. **Working in it** — image `assets/images/desktop/app-session-versions.webp`
   A session in progress: the model runs the TIA tools one by one (`project_status`, `workspace_describe`, `open_project`, `project_version_query`, `git_status`), the chat shows its planning and the to-do list, and the Versions panel renders the last two commits with every changed block and whether the change touched the interface, the code, the comments or the block properties. This is the shipped UI, not a mockup.

Note: The setup never bundles the DSH runtime: it reuses what you have, or fetches the official package from `download.deepseek.com`. A DSH newer than the verified 0.2.1-rc.2 is allowed after a warning; one older than 0.2.1-rc.1 is refused rather than overwritten. On an offline machine, install DSH and WebView2 first — after that the wizard works without a network, because nothing is fetched from npm.

### Other install paths
Note: Same blueprint, different packaging. Use these when you cannot run an installer, want the current worktree, or need a single bundle.

**A · Release zip** — no build, no Node; installs into a versioned profile under `%USERPROFILE%\dsh-automation-suite-home` and starts DSH from a console. Needs an installed DSH.

```powershell
$ .\install.cmd
$ .\start.cmd
```

Download `dsh-automation-suite-<version>.zip` from Releases and extract it first. Double-clicking the two `.cmd` files works too; `install.cmd` avoids the PowerShell execution-policy block on downloaded scripts.

**B · From source** — for development. Runs the current worktree; needs Node 22.19+ and the pnpm bundled with DSH; `-Mode pack` tests the real tarballs.

```powershell
$ git clone https://github.com/voltarenyah/dsh-automation-suite
$ cd dsh-automation-suite
$ pwsh -NoProfile -File scripts\start-env.ps1
```

The starter builds the packages, materializes the profile in `%USERPROFILE%\dsh-automation-suite-home`, links the local packages, starts `dsh` and opens the tokenized URL. Use `-Mode pack` to test the release tarballs and `-Restart` to replace a running instance.

**C · One plugin only** — advanced. Every package is its own bundle; install its tarball and add the matching `/tools` row when it has one.

```powershell
$ dsh plugin --profile web add <tarball-url>
```

TIA, PLCSIM, graph and git expose model tools only after a `/tools` row is added; engineering-context also needs TIA and git at runtime. The Architecture page has the surface matrix.

Note: These three paths assume DeepSeek Harness is already installed: the zip installer exits with an error if it cannot find `dsh.cmd`. Only the desktop setup can fetch the runtime for you.

### First start
Note: From an opened window to a working session.

1. **Open the window — or the printed URL**
   The desktop shell starts DSH for you and loads the tokenized URL into its own window; the zip path prints `dsh web: http://127.0.0.1:<port>/?token=…` in the console instead. Either way the token is required and changes on every start — the bare port returns 401, so do not share the URL.
2. **Add a model API key**
   Settings → Models, or the first-run prompt. The release profile defaults to `dsh-opencode-go` / `deepseek-v4.1-flash`; add that provider's key or pick another model. Credentials stay in this DSH_HOME.
3. **Add a workspace**
   Point at the project folder. The left sidebar is a registry stored in DSH_HOME, not a scan of the disk, so every workspace is added explicitly; since 0.2.3 the picker is the app's own directory surface, not the Windows folder dialog.
4. **Verify the engineering path**
   TIA: open or create a project and make a read-only call. Graph: `create_engineering_project` should report a built database; “not built” often means .NET 8 is missing — install Microsoft.DotNet.Runtime.8. Git: run `git --version`.
5. **Quit from the menu, not the X**
   The window's close button hides it to the tray and the app — TIA controller included — keeps running; use `Application → Exit` or the tray's Exit to stop everything. On the zip path, closing the console stops the service and `start.cmd` starts it again. Sessions, workspaces and credentials persist either way.

#### First TIA call
Note: The first tool call that touches TIA is gated by Portal itself: “Openness access (0033:…)” asks whether `TiaOpennessV17Min.Controller.exe` — the controller under the profile's `node_modules` — may attach to the running instance. That dialog is Siemens', not the suite's, and there is no silent bypass. Yes grants the current session only; Yes to all also saves the authorization in the V17 whitelist (`HKLM\SOFTWARE\Siemens\Automation\Openness\17.0\Whitelist`), which is what stops the prompt coming back after a rebuild or an upgrade — writing it needs an elevated TIA. No makes the call fail: retry and allow it.

Image: `assets/images/tia/openness-access-dialog.webp` (dialog crop; full window at `assets/images/tia/openness-access.webp`)

#### Large projects and long calls
Note: The default `requestTimeoutMs` is 300000 (5 minutes). Exporting a few hundred blocks already takes about 87 s, and compiling a large project can take more than 10 minutes. Raise it before the first large TIA or graph call.

```yaml
- id: tia-openness-v17-min
  config:
    requestTimeoutMs: 900000
- id: engineering-graph
  config:
    requestTimeoutMs: 900000
```

Note: The same value bounds a single-device graph build; a 1,376-file project took about 30 s, but large projects deserve the headroom.

### Installation notes
Note: The things that most often go wrong, and the safe way to undo.

| Topic | What to know |
| --- | --- |
| DSH runtime | The desktop setup reuses an installed DSH at or above 0.2.1-rc.1 and downloads the official runtime when it is missing, checking SHA-512 and the DeepSeek signature. The zip installer only finds an existing `dsh.cmd` (or `DSH_EXE`). |
| SmartScreen | Neither the setup exe nor the zip scripts are signed. For the setup: More info → Run anyway. For the scripts, use `install.cmd` / `start.cmd` (they set a process-level bypass and pause on errors); running `install.ps1` directly may close before you can read the error. |
| Two roots | Desktop: app files in `%LOCALAPPDATA%\dsh-automation-suite`, user data in `%USERPROFILE%\dsh-automation-suite-home` with the fixed profile name `dsh-automation-suite`. The zip path uses the same home with a versioned profile. Nothing is written to `~/.dsh`. |
| Upgrade / rollback | Desktop: exit the app, then run the next setup over the old one — the shell is replaced, the app layer gets a new versioned folder, and the fixed profile's `cordis.patch.yml` overrides are backed up as `.bak-<timestamp>` and merged. Web zip: each version gets its own profile, so start the older one to roll back. |
| Uninstall | Desktop: Windows Settings → Apps → DSH Automation Suite removes the shell, the app layers and the shortcuts; `dsh-automation-suite-home` is kept. Delete user data with `cmd /c rmdir /s /q "%USERPROFILE%\dsh-automation-suite-home"`; never use a recursive delete that follows junctions. |
| External runtimes | The shell needs Evergreen WebView2 (the setup installs the bootstrapper when it is missing). Only TIA and PLCSIM need Siemens software. The graph needs .NET 8; git needs `git.exe`; Excel/PDF need no Office or Acrobat. TIA and PLCSIM licensing is yours. |
| Network / proxy | The desktop setup needs GitHub for the download and `download.deepseek.com` for DSH/WebView2 when they are missing — never npm, because the profile ships materialized. The zip path needs GitHub and npm; on an isolated network, mirror the registry or pre-stage the tarballs. |
| Ports | The shell starts DSH with an OS-assigned free port (`--port 0`), so there is nothing to configure — the window loads whatever port was picked. The zip path's `start.cmd` picks 3093+ automatically instead; it also accepts `-Port`, and `-NoOpen` suppresses the browser. |
| Desktop shell | 0.2.3 ships the WebView2 shell and the per-user installer: Start-menu entry, optional desktop shortcut, tray, single instance, logs reachable from the tray's Open logs. There is still no auto-update — upgrade by running the next setup. |
| Security | Treat the tokenized URL as a secret; it grants the session. Keep DSH_HOME out of source control — credentials and sessions live there. |
