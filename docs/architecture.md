# 目标架构：三个插件族

> 本文描述本发行版**要长成什么样**：解决方案由哪些插件组成、各自的职责与边界、
> 它们之间靠什么契约协作。
>
> ⚠️ **除标注"已实现"的部分外，本文全部是目标架构，不是现状。** 现状与进度见
> [`roadmap.md`](roadmap.md)；为什么这样分层见 [`vision.md`](vision.md)。
> 本文里的接口名、节点/边类型、选型都是**候选**，标着"待定"的地方就是还没定。

## 1. 三个插件族总览

本解决方案不是一个大插件，而是**多个插件，各自负责一个方面**：

| # | 插件族 | 对应层 | 一句话职责 | 现状 |
|---|---|---|---|---|
| **1** | **工控软件接口插件族**<br>（以 TIA 为例即 `tia-openness`；**按软件版本 × 能力层级**切分：V17/V18… × **min/std/pro**） | ① 接入层 | 与工控软件对接，**读写工程对象**；为后续分析提供**素材**与**验证工具**；并**附带文档**说清何时调用、怎么调用、数据怎么用 | 🟡 已有第一个成员：`@voltarenyah/dsh-tia-openness-v17-min`（V17 × min，定位是**验证基础功能**） |
| **2** | **工程上下文管理插件** | 横向（作用域） | 面对用户的**多个 TIA 项目 × 多个分支 × 多个历史版本**，管理工程上下文，在会话中就某个工程问题**暴露出恰当的工程上下文**；对**工程对象做优化适配**并用「待办清单」式载体承接工程变更上下文 | ⬜ 规划中 |
| **3** | **工程知识图谱管理插件** | ② 语义层 | **准确翻译 XML 中的 PLC 语法**（兼容性强），把工程源文件解析成 LLM 便于处理的信息：**解析 XML → 建立图数据库 → 暴露接口**提供所需工程细节 | ⬜ 规划中 |

插件编号沿用需求的表述顺序（1 → 2 → 3），**它不代表实现顺序**；依赖关系见 [§7](#7-依赖与推进顺序)。

## 2. 为什么这样切：三条正交的轴

三个插件族分别管三件不同的事，任意两件都不能互相替代：

| 轴 | 由谁负责 | 回答的问题 |
|---|---|---|
| **素材（access）** | 插件族 1 | 内容**从哪来、往哪写** —— 只有它能与工控软件对话 |
| **语义（understanding）** | 插件族 3 | 这些源文件**意味着什么** —— 只做解析与建模，不碰设备 |
| **作用域（scope）** | 插件族 2 | 现在谈的是**哪个项目的哪个分支的哪个版本** |

两个由此推出的关键结论：

- **插件族 1 是唯一的"素材源"，也是唯一的"验证器"。** 它一方面导出源文件供插件族 3 解析，
  另一方面——这是它不可替代的价值——**任何改动最终都要经它写回真实工程并编译验证**。
  没有它，模型只能给"看起来对"的建议。
- **插件族 2 不产出工程语义，但决定语义的适用范围。** 用户的资产是"多项目 × 多分支 × 多版本"，
  没有作用域管理，会话里给出的答案就无法确定对应哪一份代码 —— 结论对了也可能对不上版本。

## 4. 各插件族的职责与边界

### 4.1 插件族 1 · 工控软件接口插件

- **职责**：与工控软件对接，读写工程对象；为后续分析提供素材与验证工具。

#### 期望：把工控软件暴露的能力，整体变成 LLM 的能力范围

以 TIA 为例，**TIA Openness manual 里暴露出的能力与接口，都应该能落进 LLM 的能力范围**。
这里有个容易做偏的地方：**光暴露接口不算达成**。真正的标准是三件事都能被模型搞清楚 ——

| # | 模型必须能搞清楚 | 载体 |
|---|---|---|
| 1 | **什么时候调用**这个工具（触发条件、前置状态） | 工具 description（模型一定会读到）+ 文档 |
| 2 | **怎么调用**（参数、顺序、约束、典型组合） | 随包 **skill** 资源 |
| 3 | **调用后拿到的数据怎么用**才能得到更有价值的信息（结果解读） | 随包 **skill** 资源 |

> 结论：**文档是交付物的一部分，不是附属品。** 一个接口"能调通"但在文档里说不清何时用、
> 怎么用、结果怎么读，就不算把这个能力交给模型。文档与工具必须同步演进，
> 并靠一致性校验（工具签名/枚举变了而文档没变就失败）来守住（[`decisions.md`](decisions.md) D4）。

**还要提前考虑的一件事**：后续要支持**用户根据自己的项目特点自己写 skill** 供 agent 调取 ——
也就是"通用能力文档"与"项目专属知识"两层的划分与加载规则（形态待定，见
[`open-questions.md`](open-questions.md) **A12**）。

#### 两条切分轴

插件族 1 不是"一个插件对应一个 TIA 版本"这么简单，它有**两条轴**：

| 轴 | 取值 | 现状与方向 |
|---|---|---|
| **软件版本** | V17 / V18+ / … | 🟡 只做 V17；等第二个版本到来时抽公共 core 包（[`decisions.md`](decisions.md) D3） |
| **能力层级** | **min → std → pro** | 🟡 只维护 **min**（实现基础功能）；后续功能**在 min 基础上扩展**（D1） |

**能力层级按「能力范围」划分**（D1），维度是：

| 维度 | 取值 |
|---|---|
| 读写性质 | 只读 PLC 数据 / 带**回写**能力 |
| 对象域 | 硬件 / 软件 |
| 连接状态 | 离线 / 在线 |
| 覆盖范围 | PLC only / 含 HMI |
| 工程结构 | 是否含软件单元、多用户、项目库 / 全局库 |

每个层级具体囊括哪些能力**日后再详细定义**。分层的**包形态**默认"一档一个包"，但有一个前提：
min 新增的能力必须能低成本流向 std / pro —— 否则改用"内核包 + 能力包"（D2）。
另有一条硬约束：**同族两个档不能在同一个 profile 里同时生效**，
因为一个宿主进程只允许一个控制器子进程（见 [§2](#2-为什么这样切三条正交的轴)）。

#### 两副面孔（缺一不可）

- **素材源**：导出工程对象为源文件（Simatic ML / SCL / STL），附 manifest 供下游解析；
- **验证器**：把改动写回真实工程，用事务 + 写后读回 + 编译来回答"这个改动成立吗"。

- **边界**：不做语义建模（那是插件族 3），不管"哪个项目"（那是插件族 2）。
- **现状**：🟡 V17 × min 已实现（6 个工具 + 白名单控制器 + 写后验证），
  细节见根 README §4.2 与该包 README。

### 4.2 插件族 2 · 工程上下文管理插件

- **职责**：管理工程上下文，使得用户在 session 里就某个工程问题对话时，工具能暴露出
  **恰当的**工程上下文，供 LLM 生成更准确、更懂上下文的答案。
- **它要管的资产**：一个用户的**多个 TIA 项目**，每个项目可能有**多个分支**，
  每个分支又有**很多历史版本**。

#### 作用域模型：session ↔ workspace（已定，D5）

参照 DSH Web 左侧导航栏的组织方式，**workspace 是工程作用域的一级概念**：

```
新建 workspace  →  在其下启动 session  →  agent 把源 TIA 项目「打开并另存」到 workspace
      →  打开 workspace 里这个本地项目  →  导出源文件到项目路径下  →  按规则维护该路径
```

- **session 与工程项目绑定**；新启动的对话**原则上只能访问自己 workspace 下的工程项目**；
- 源项目与工作副本分离：agent 动的是 workspace 里的**副本**；
- workspace 里"放什么、怎么放"是一套**路径规则**，属于本插件族的交付物。

#### 期望一：对工程对象做优化适配

| 要适配的问题 | 结论 |
|---|---|
| **工程项目路径包括哪些内容** | 由 workspace 路径规则定义（字段级细化见 [`open-questions.md`](open-questions.md) B7） |
| **如何识别工程文件是否被更改** | **以 TIA 指纹为硬依据**（`FingerprintProvider`），不用 mtime、不用自研哈希（D6） |
| **更改怎样被区分与跟进** | 指纹是**分面**的（`Code` / `Comments` / `Interface` / `Properties` …），所以能区分"改的是哪一部分" |

指纹的适用范围（已核对本仓 `skills/` 语料）：**块（FB/FC/OB/DB）与 PLC 数据类型可用，标签表没有**；
更粗的粒度另有 `PlcChecksumProvider`（整个 PLC 程序是否变过）与 `SafetySignatureProvider`（Safety 专用）。

> 代价：**变更检测必须开项目**（指纹来自 Openness，不是文本分析）。想离线判断"变没变"不在本方案的路径里。

#### 期望二：用"待办清单"式工具承载工程变更上下文

针对用户的工程问题，用**类似 Todo 清单**的载体承接**工程变更上下文**，并在**合适的时候**
把它交给 LLM（或呈现给用户），用来**辅助判断用户的真实意图** ——
用户说"把这块改一下"，他可能正在做的是某个更大的重构，变更清单就是判断依据。

#### 期望三：版本之间变更明确易读，且工程对象可交叉关联

- **明确易读**：版本之间的差异要人能读懂、模型也能读懂，不是一堆文件级 diff；
- **交叉关联**：一对**相关联的工程对象**要能被关联起来（跨版本的对应关系）——
  身份键用 **TIA 在导出时提供的唯一 id**（D7；V21+ 另有 `ObjectIdentifierProvider`）。

#### 工作循环：真相源是 `.ap17`（D9）

```
用户在 TIA 里改 .ap17  →  指纹比对找出变化的块  →  只导出这些块  →  更新图  →  交给模型
```

- **`.ap17` 是真相源**：用户可以直接改项目，改完再对比、导出被更新的块；导出物是**派生视图**；
- 变更检测必须**先于**导出 —— 否则要么全量重导（慢）、要么拿旧内容回答（错）。

#### 其他

- **至少要管两件事**：**TIA 项目的存储路径**；**git 版本**（分支、历史版本、"当前谈的是哪一版"）——
  其中**可能又需要引入 git 的底层能力**（引入方式见 [`open-questions.md`](open-questions.md) A8）。
- **核心产出**：一个明确的**工程作用域**概念 —— 会话里任何结论都能回答
  "这是哪个项目 / 哪个分支 / 哪个版本"。
- **边界**：它不解析工程内容、也不与工控软件对话；它决定**范围**，不决定**含义**。

### 4.3 插件族 3 · 工程知识图谱管理插件

- **职责**：基于从设备（经插件族 1）导出的工程源文件，解析为 LLM 便于处理的信息。
- **三段式**：
  1. **解析 XML**：工程源文件 → 工程要素；
  2. **建立图数据库**：把要素与关系落成图（"谁调用谁""谁用了哪个类型""这个变量属于哪张表"）；
  3. **暴露接口**：按 LLM 的需求提供**工程细节**（要什么给什么，而不是把整个项目塞给它）。

#### 底座：SQLite + Graph DB（已定，D8）

图底座采用 **SQLite + Graph DB** 这条技术路径（已在另一个代码库验证可用），
**不引入服务型图数据库** —— 方案跑在工程师本机，不应要求额外部署。
分区/更新策略（A10）与语法翻译深度（A11）仍待定。

#### 期望：准确翻译 XML 中的 PLC 语法，兼容性强

- **准确**：把 XML 里的 **PLC 语法**翻译对 —— 块的语言（SCL/STL/LAD/FBD/GRAPH）与语义、
  数据类型、实例关系都要忠实还原，不能"大概齐"。**这是本族的第一质量目标**，
  图数据库只是承载它的手段。
- **兼容性强**：能应对不同来源、不同版本的导出物（不同 TIA 版本、不同语言、不同写法），
  而不是只认手上的那一个样本。
- **关系边的两个来源（待定，见 [`open-questions.md`](open-questions.md) A13）**：
  - **自己解析 XML**（离线可用，但"谁引用了谁"要靠推断）；
  - **从 TIA 取交叉引用** —— Openness 的 `CrossReferenceService` 直接给 unused / using / used-by，
    是**权威答案**但要开项目。
  两者是否都以、以谁为准、如何交叉校验，尚未决定。

- **候选的图模型**（待定，需与实际解析结果对齐）：

  | 类型 | 候选 |
  |---|---|
  | 节点 | 块、PLC 数据类型（UDT）、标签表、标签、用户组、I/O |
  | 边 | 调用、包含（组层级）、实例化、读写（标签）、引用类型 |

- **边界**：只做静态解析与查询，不碰设备、不做版本管理。写入工程的唯一通道是插件族 1。

## 5. 会话中的"恰当的工程上下文"

这是插件族 2 与 3 共同的验收目标，也是整个方案能不能用的关键。

1. **作用域显式**（已定，D5）：**session 绑定 workspace**，workspace 对应一个工程项目；
   新会话只能访问自己 workspace 下的项目。换项目 = 换 workspace，是显式动作而非悄悄漂移。
2. **分级暴露**（待定）：全局摘要（有哪些块、分组、规模）→ 按需下钻（某个块、某条调用链）。
   上下文预算必须有上限，**不能随项目规模线性增长**。
3. **可溯源**：任何分析结论都要能指回"哪一版、哪个文件、哪个块"，否则模型给的建议
   可能对应一份已经不存在的代码。身份靠 TIA 唯一 id（D7）。
4. **失效可感知**：源文件、图、作用域三者版本不一致时，必须能检测并明确报告
   （检测手段是 TIA 指纹，D6），而不是拿旧图当新项目回答。

## 6. 插件间契约

| 契约 | 从 → 到 | 形态 | 状态 |
|---|---|---|---|
| 导出的工程素材 | ① → ③ | 导出目录 + manifest（现有插件已产出 `_tia-openness-manifest.json`，含逐文件 SHA-256） | 已在用 |
| **变更检测** | ② → ① | TIA 指纹（`FingerprintProvider`，分面：Code / Interface / Comments / Properties…） | 已定（D6），V17 待实测 |
| **对象身份** | ① → ②③ | 导出物携带的 TIA 唯一 id | 已定（D7），稳定性待验证 |
| 写回与验证 | ③/② → ① | 导入 + 编译 + 写后校验，结果作为数据返回 | 已有的能力 |
| 作用域 | ② → ①③ | 「项目 / 分支 / 版本」标识 + 该版本对应的导出物位置 | 随 D5 收窄 |
| 工程查询 | ③ → LLM | 图查询接口 + 分级摘要 | 待定 |
| **变更上下文** | ② → LLM | 「待办清单」式的工程变更上下文，在合适的时候暴露，用于判断用户意图 | 待定 |
| **能力文档** | ① → LLM | 每个能力/工具的"何时调用 / 怎么调用 / 结果怎么用"三问 | 已定（D4） |
| 版本操作 | ② → git | 分支/历史/差异/工作副本物化 | 见 [`open-questions.md`](open-questions.md) **A8** |

## 7. 依赖与推进顺序

```
① 接口插件族 ──素材──▶ ③ 知识图谱插件 ──语义──┐
   （已验证）            （可离线开发）          ├──▶ 会话中有用的工程上下文
        ▲                                       │
        └──────────── ② 工程上下文管理插件 ──────┘
                        （决定作用域；可先做最小版）
```

- **① → ③ 是硬依赖**：图谱的输入就是接口插件的导出物；好消息是③**纯文本解析，
  不依赖 TIA / Windows，可离线开发与测试**。
- **② 相对独立**：它管 workspace、路径与版本。**A5 定下来之后它更是如此** ——
  workspace 建立 + 变更检测（指纹）+ 版本管理**都不依赖图谱**，可以先独立产生价值
  （"告诉我这个项目自上次以来哪些块变了"本身就有用），再长出真正的多分支/多版本能力。
- **① 自己有两条推进线**：**横向**加软件版本（V18+）、**纵向**升能力层级（min → std → pro）；
  每条线上都必须同时补**文档**，否则接口加了模型也用不对。
- **建议顺序**：①（补完）→ ③（拿到语义）→ ②（把语义限定到正确的范围）。
  这只是基于依赖关系的建议；由于 ② 已确认可以脱离图谱独立起步（D5/D6/D9），
  按需求编号 1 → 2 → 3 推进**也成立**，两者只差优先级，不再是阻塞问题。

## 9. 设计约束（延续 [`vision.md`](vision.md) §4）

- **文档即交付物**：接口不配"何时调用 / 怎么调用 / 结果怎么用"的说明，就不算交到模型手上；
  文档与工具必须同步演进。
- **准确优先于覆盖**：PLC 语法的翻译要忠实，宁可少支持一种写法，不要猜。
- **兼容性靠设计而非运气**：对不同版本 / 不同来源的导出物要能识别差异并按能力降级，
  而不是只认手边那一个样本。
- **写入只有一个通道**：图数据库与上下文管理永远不直接改工程，改动一律经接口插件写回并验证。
- **不向模型暴露任意代码执行**：能力面始终是数据化操作与查询。
- **默认安全**：破坏性操作 fail-closed。
- **上下文经济**：知识库、图、工程内容都不占常驻上下文，按需加载、按需展开。
- **证据可回溯**：任何工程结论都要能指到具体版本、文件与块。
