# 愿景：让 LLM 真正能访问、理解与操作 PLC 工程

> 本文说明 **dsh-automation-suite 为什么存在**：它要解决什么问题、把解决方案分成哪几层、
> 每层的职责与接口是什么。逐项的进度与缺口见 [`roadmap.md`](roadmap.md)；
> 仓内已实现能力的用法见根 [`README.md`](../README.md)。

---

## 1. 问题

工业控制领域的 **PLC 项目文件无法被 LLM 很好地访问、理解与操作**，因此 LLM 在这个领域
能提供的帮助极其有限。

这不是"模型不够聪明"，而是**链路上有硬障碍**：

| 障碍 | 表现 |
|---|---|
| **访问不到** | 项目是专用工程软件的私有格式（TIA Portal 的 `.ap17` 等），没有文本表示；不装那套软件、不通过它的接口，内容取不出来也写不回去 |
| **理解不了** | 即便拿到了导出文件（XML/SCL/STL），它们描述的是**工程对象**：块、调用关系、数据类型、标签表、I/O、组层级。没有这一层的还原，模型看到的只是文本 |
| **不敢操作** | 一次改动是否成立，只有编译与写后验证能回答。缺了这层保障，模型给出的是"看起来对"的建议，工程上不可用 |
| **管不起来** | 工程软件普遍缺项目级能力（最典型的是版本管理）。二进制工程文件直接进 VCS 只能得到"变了 / 没变"，得不到**工程意义上的变更** |

四者是一条链：前面不通，后面的价值都拿不到。

## 2. 打通之后能得到什么

工具层的障碍一旦打通，并且工程内容被还原成模型擅长处理的形式，就可以提供：

- **程序诊断** —— 结合真实代码与工程约束定位问题；
- **程序分析** —— 调用关系、影响面、命名与结构一致性、可维护性；
- **编写建议** —— 新增/修改块、外部源、标签表，并**编译验证**改动成立；
- **项目级帮助** —— 借助工程软件预留的项目级接口，管理那些软件本身没做的事，
  比如版本管理、变更追溯、变更影响分析。

## 3. 分层方案

解决方案被拆成三层，**每层解锁下一层**：

```
┌──────────────────────────────────────────────────────────────────────────┐
│ ③ 管理与协作层                                                            │
│    在工程软件预留的项目级接口之上，做它本身没有的能力                       │
│      • 项目级版本管理（导出为文本 → 外部 VCS → 差异/提交 → 可回滚）          │
│      • 变更影响分析、工程意义上的 diff、多用户/库管理                       │
│    消费：② 的工程模型 + 外部工具（git）                                    │
└───────────────────────────────▲──────────────────────────────────────────┘
                                │ 工程语义
┌───────────────────────────────┴──────────────────────────────────────────┐
│ ② 语义层                                                                  │
│    解析源文件 → 还原工程信息与要素 → 转成 LLM 擅长处理的格式                 │
│      • 要素：块、调用关系、数据类型（UDT）、标签表、I/O、组层级               │
│      • 形态：结构化、可导航、按需展开（而不是把几十 MB XML 塞进上下文）       │
│    产出：可推理的工程上下文 → 模型据此给出诊断 / 分析 / 编写建议             │
└───────────────────────────────▲──────────────────────────────────────────┘
                                │ 程序源文件（Simatic ML / SCL / STL）
┌───────────────────────────────┴──────────────────────────────────────────┐
│ ① 接入层                                                                  │
│    通过工控软件预留的接口（TIA Openness 等）把程序源文件取出来、写回去       │
│      • 白名单操作、事务、写后验证；不向模型暴露任意代码执行                  │
│    产出：程序源文件                                                        │
└──────────────────────────────────────────────────────────────────────────┘
```

**本发行版就是这条链路的载体**：它由**多个插件**组成，每个插件负责其中一个方面 ——
**工控软件接口插件族**（①，按版本各出一个）、**工程上下文插件**（作用域）、
**工程知识图谱插件**（②）。三者的职责、边界与契约见
[`architecture.md`](architecture.md)，现状对照见 [`roadmap.md`](roadmap.md) §2。

### 3.1 ① 接入层：打通工具层面的障碍

- **做什么**：调用工程软件预留的公开接口，把工程内容导出成程序源文件，改完再导回。
- **为什么必须用它自己的接口**：项目格式是私有的，绕过软件去解析二进制格式既不现实也不安全。
- **设计要点**：把"任意代码执行"压缩成**一组数据化操作**（路径、块名、枚举）；
  写入必须**可回滚**（事务）且**可验证**（写后读回），否则模型改工程这件事不可接受。
- **今天的实例**：TIA Portal V17 Openness 的块级读写（见根 README §4.2）。

### 3.2 ② 语义层：把工程信息还原出来

- **做什么**：解析①产出的源文件，还原成工程对象模型，再转成 LLM 擅长处理的表示。
- **还原什么**：块与块的**调用关系**、数据类型（UDT）与实例、标签表与 I/O 映射、
  用户组层级、块属性（编号、语言、时间戳）等**工程要素**。
- **为什么不能只给 XML**：上下文有限，而一个真实项目导出后是几十 MB / 上千个文件；
  模型需要的是"先看全局摘要，再按需展开某个块"，而不是全文灌入。
- **成果形态**：可推理的工程上下文 —— 模型据此给出**程序诊断、分析与编写建议**。
- **与①的边界**：①负责"拿到文件"，②负责"读懂文件"，两者不能互相替代。

### 3.3 ③ 管理与协作层：补齐工程软件的短板，管好"在谈哪一版"

- **做什么**：在①②之上做工程软件本身没有的能力。它管两件互相关联的事：
  **作用域**（这是哪个项目的哪个分支的哪个版本）与**工程软件缺失的项目级操作**（如版本管理）。
- **为什么需要作用域**：一个用户的资产通常是**多个项目 × 多个分支 × 多个历史版本**。
  没有作用域，会话里给出的答案就无法确定对应哪一份代码 —— 结论可能对，却对不上版本。
- **典型场景 —— 版本管理**：TIA Portal 没有项目级 VCS，`.ap17` 是二进制工程文件，
  直接纳入 git 只能得到"变了 / 没变"。可行路径是
  **导出为文本源 → 交给外部工具（git）→ 需要时导回**；再让模型生成
  **工程意义上的**差异说明与提交信息（改了哪个块、谁受影响）。
- **为什么依赖前两层**：没有①取不出文本，也写不回去；没有②，diff 只是文本 diff，
  既读不懂也不足以支撑影响分析与回滚。
- **今天的实例**：通用的 12 个结构化 git 工具 + 破坏性命令闸门（见根 README §4.3）——
  底座已经有了，但**尚未与 PLC 项目打通**，也还没有作用域的概念。

## 4. 贯穿三层的设计原则

1. **只暴露数据，不暴露任意代码执行** —— 模型能表达的是路径、名字、枚举，不是脚本。
2. **写入必须可回滚、可验证** —— dry-run 预演 → 事务提交 → 写后读回验证；任一环缺失就不算完成。
3. **默认安全（fail-closed）** —— 破坏性操作默认拒绝；需要放行时显式调整策略。
4. **上下文经济** —— 知识库与工程内容都不占常驻上下文，按需加载、按需展开。
5. **证据可回溯** —— 结论要能指到具体文件/行号或实测记录；"上游文档这么说"与"本项目实测过"
   必须分开陈述（见根 `AGENTS.md` §4 与各包 `docs/`）。

## 5. 术语

| 术语 | 含义 |
|---|---|
| **PLC** | 可编程逻辑控制器，工业现场的控制设备 |
| **TIA Portal** | Siemens 的自动化工程软件（本项目对标 **V17**） |
| **Openness** | TIA Portal 提供的公开 API，允许外部程序操作项目 |
| **块 / Block** | PLC 程序的基本单位（OB/FB/FC/DB 等） |
| **UDT** | 用户自定义数据类型 |
| **标签表 / Tag table** | PLC 变量的符号定义 |
| **Simatic ML** | TIA 用于导出/导入块的 XML 表示 |
| **workspace（工程工作区）** | 工程作用域的一级单位：一个 workspace 对应一个工程项目，session 在其下启动并**只能访问该 workspace** 内的项目（见 [`decisions.md`](decisions.md) D5） |
| **指纹（fingerprint）** | TIA 为块/PLC 数据类型提供的**分面**变更标识（代码、接口、注释、属性…），用于判断"改没改、改了哪一部分"（D6） |
| **接口插件族 / 工程上下文插件 / 工程知识图谱插件** | 本发行版的三类插件：与工控软件对话（唯一素材源与验证器）／管工程作用域（哪个项目 × 分支 × 版本）／把工程源文件解析成可查询的图。**只有接口插件族是"一族多成员"**（成员 = 软件版本 × 能力层级）；另外两个都是单一插件。注：早期文档里写作「族 1 / 族 2 / 族 3」，该编号已废止 |
| **接入层 / 语义层 / 管理层** | 本文 §3 的三层划分 |

## 6. 非目标

- **不是**绕过厂商软件去读写私有二进制格式的工具；
- **不是**要替代 TIA Portal 或任何工程软件的界面；
- **不是**让模型自由执行工控代码的通道 —— 能力始终限定在显式白名单操作内；
- **不是**"支持所有厂商、所有版本"的承诺：当前只覆盖 TIA Portal V17 的块级能力，
  扩展范围见 [`roadmap.md`](roadmap.md) §4。
