### A1 · 接口插件族：能力层级 min / std / pro 按什么维度划分？

**为什么要问**：它决定 std / pro 各自要做什么、"更多更全的能力"具体指哪些，
也是后面 A2（包结构）、B5（覆盖率口径）的前提。

**候选维度**
- A. 按 **Openness 能力域**划分（块 / 类型 / 标签表 / 硬件组态 / 在线 / 库 / 多用户 / HMI…）
- B. 按 **使用频率与价值**划分（高频先做，长尾后做）
- C. 按 **风险**划分（只读的先做，写入/在线操作后做，且需要更严的验证）
- D. 以上组合，例如"只读 + 高频"入 std，"写入 + 低风险"入 std，"在线/多用户/库"入 pro

**倾向**：D，且**以"是否需要更严的写入验证"为主线** —— 这与现有 min 的能力（导出/导入/编译 + 事务 + 写后验证）
是同一套安全语义，比较容易保持一致性。

**答复**：
按照能力范围来划分。有以下维度，比如是读PLC数据，还是带回写能力的。还有硬件/软件维度。还有离线/在线维度，PLC only/include HMI，是否包括对软件单元，多用户，项目库全局库支持。具体每个版本囊括哪些能力，这个需要后面再详细定义，目前先只维护min实现基础功能。后续增加额外功能时会在min的基础上扩展。

### A8 · 工程上下文插件：git 底层能力怎么引入？

**为什么要问**：你提到"其中可能又需要引入 git 的底层能力"。仓库里已有一族结构化 git 工具（12 个），
但它面向的是普通仓库操作，不一定够用。

**候选**

**同时需要你判断**："底层能力"具体要哪些原子操作？例如：历史遍历、树/blob 读取、
工作副本物化到指定版本、两版之间的对象级差异、局部提交。

**倾向**：C 起步（与现有 `execFile` + 参数数组的安全风格一致，无新依赖），
只有出现性能或并发瓶颈时才考虑 B；A 作为面向模型的上层工具保留。

**答复**：
我无法现在直接给你答案。但是我有几个问题。
引入git库对于dsh发行版来说是常规操作吗？它还是以插件的形式存在的吗？
因为这个底层git能力并非直接暴露给用户的，而是被工程上下文插件调用实现功能的。
另外直接让agent调git命令是否会存在不确定性，比如路径搞错了，参数忘记带等等，如果希望一致性好的话，是不是还是要用插件对git做二次封装只暴露工具更好。

**补充分析（供决策，来自本仓约定与已实现代码）**：

- **引入第三方库是常规操作**：DSH 插件就是普通 Node 包，可以在 `dependencies` 里声明任何 npm 依赖，
  由 profile 安装时落进它的 `node_modules`。本仓唯一的限制是**不许把 `@deepseek-ai/*`（宿主运行时）

- **它不必是插件**：`packages/` 下的包目前都带 `dsh.bundle.patch`（= 插件），但没有这个字段的包

- **"让 agent 调 git 命令"和"插件内部调 git"是两件事**，你担心的不确定性只属于前者：
  - **插件内部调用**：参数在**代码里**拼好（`execFile('git', [明确参数])`），

- **你的结论我认同并且已经写进架构**：**不要**把原始 git 能力暴露给模型，而是由插件做二次封装、

  这与"写入只有一个通道"是同一个思路。现有那 12 个面向模型的 git 工具是**通用**能力，
  与 PLC 工程无关；上下文插件**不应依赖模型去调它**，而应自己调 git。

**答复**（2026-10-14，随工程上下文插件的设计定稿）：

- **选 C：直接调 `git` 命令，但封在插件内部**，做法照抄

  （`execFile` + 显式参数数组、`core.quotepath=false`、`--no-optional-locks`、`GIT_TERMINAL_PROMPT=0`）。
  **不引入 git 库**（B 只在出现性能/并发瓶颈时才考虑，目前没有任何证据需要）。

### A10 · 工程知识图谱插件：图怎么分区、怎么更新？

**为什么要问**：你有"多项目 × 多分支 × 多版本"，图的份数与重建策略直接决定存储与响应。

**候选**
- A. 按「项目 + 版本」各一份图（隔离干净，份数多）
- B. 一份图 + 版本属性（省空间，查询要带版本条件，容易写错）
- C. 按项目一份图，版本用快照/差异链表示

**更新方式候选**：全量重建（简单可靠） / 增量更新（省时，但要处理删除与重命名）
—— 注意 A7 的对象身份问题在这里会再次出现。

**倾向**：C + 全量重建起步（单项目重建是分钟级，可接受），性能不够再上增量。

**建议答复（草案 · 由 mcp-knowledge 的实测结论起草，待你确认或改写）**：

**分区**：**按设备（PLC）一份 `<设备>/plc-knowledge.db`**，随工程目录走、不进 Git。
一份图里不塞多个版本，也不做"一份图 + 版本属性"（候选 B 让每次查询都得带版本条件，最容易写错）。
版本维度交给工程上下文插件的快照/指纹表达，**图本身不认识版本** —— 与 D6（指纹是硬依据）、
D9（`.ap17` 是真相源）同向。参考实现的口径是"databases are not shared across devices or
worktrees"，粒度实际落在「工作树 × 设备」，即候选 A/C 的细化。

**更新**：**两条路径都要**，参考实现两条都已实现并在真实项目上跑过：
- **权威重建**：全删 + 单事务批量插入（`ingest_source`）。基线刷新与 schema 变更走它。
- **部件级增量**：按相对路径**事务性替换**指定部件（`update_components`）。靠三张溯源表
  （`source_components` / `source_component_nodes` / `source_component_edges`）只摘掉旧部件
  拥有的节点与边，**保留仍被其他部件引用或占用的图数据**，再并入新部件的子图。
  这正是 roadmap §3 第 8 项（工程上下文插件工作循环）"**只导出变化的块 → 更新图**"缺的那一侧。
- **安全阀（不要省）**：库里没有溯源信息 → 报 `COMPONENT_PROVENANCE_REBUILD_REQUIRED`
  要求先全量重建；部件身份与库中记录不符 → 报 `COMPONENT_IDENTITY_MISMATCH`。**不猜**。

**顺带解掉 A7 的对象身份与 D7 的阻塞**：不需要清单提供 `id`（缺口见 `MANIFEST-GAP-ANALYSIS.md:46`，
`tool-surface.md:387` 记为卡住 W8、roadmap §3 第 10 项）。参考实现用**自算的确定性身份**：
`(根元素, 对象名)` + 相对路径 + 内容哈希；同一份导出永远得到同一套 ID。

**要比参考实现多做一步**：内容哈希必须**归一化** —— 先剥掉 `<DocumentInfo><Created>`
（`MANIFEST-GAP-ANALYSIS.md` §3 已证明它每次导出都变，接口插件族的 `sha256` 因此"不能用作变更检测的键"）。
参考实现的 `contentHash = SHA256(原始文件字节)` 没有这一步，会对"内容没变但重新导出过"报伪 stale。

**答复**：
一个workspace下面的每个PLC device一张图。初次重建，后续增量更新。
一个workspace下的多个分支暂不考虑。
区分块有没有变用每个块各自的fingerprint，除非没有fingerprint用contenthash

- A. **结构级**：块清单、属性、组层级、调用关系、类型与标签关系（不解析块内语句）
- B. **语句级（浅）**：解析 SCL/STL 的调用与变量读写，不做完整语义分析
- C. **语句级（深）**：完整 AST / 控制流 / 数据流，能回答"这个变量在哪里被写"

**同时需要你判断**：块语言怎么排？现在导出实测见过 SCL / STL / LAD / FBD / GRAPH，
其中 **LAD/FBD 是图形化语言**，XML 里是网络/触点的结构化描述，与 SCL 完全不是一套解析逻辑。

**倾向**：B（先把调用与变量读写做出来，这正是诊断与分析最需要的），
LAD/FBD 先只做结构级（A）并在结果里明确标注深度。

**建议答复（草案 · 由 mcp-knowledge 的实测结论起草，待你确认或改写）**：

**深度可以上调**，不必停在倾向的 B —— 参考实现已在真实 V17 导出物上做到语句级：

| 块语言 | 实际深度 | 证据（`src/Mcp.Knowledge/Parsing/`） |
|---|---|---|
| **LAD / FBD，含 Safety 的 `F_LAD` / `F_FBD`** | **语句级**：FlgNet 几何 + 访问点 → 类 SCL 语句 | `ProgramBlockLogicYamlWriter.cs:83`、`:247-253`（`IsLadOrFbd` 显式含 `F_LAD`/`F_FBD`） |
| **SCL** | **语句级**：`<NetworkSource><StructuredText>` token 流 → 语句 | 同文件 `:112-140`；`ProgramSemanticReference.cs:319,357` |
| **STL（AWL）** | **未见支持** | 无 `StatementList`/AWL 处理路径 |
| **GRAPH** | **未见支持** | 落入显式失败分支（`:142-147`） |

**关键：深度不是隐含的，而是随结果一起标注的。** 每个网段带 `language` /
`translationLanguage`（`scl` 或 `scl-like`）/ **`confidence`（`exact` / `partial` /
`untranslated`）** / `notes[]`；只要有一个指令是泛化渲染的，网段首行会被插入
`// Translated generically: pin semantics of one or more instructions were not verified.`
（`:213-216`、`:242`）。这正对应 roadmap §4 的"**降级不崩**"与"**宁可明确报不支持，不要猜**"，
并且直接回答 B14（"准确"如何验收）：**准确率可以按 confidence 分级统计，而不是只有"对/错"**。

**要一起接受的两条**：
1. 未覆盖的指令**不硬失败**，按连线拓扑泛化渲染并显式标注 —— 但"泛化渲染"≠"准确翻译"，
   汇报与统计里必须分开计。
2. "LAD/FBD 先只做结构级"这条倾向可以取消，改为**按语言逐项记录置信度**。
   推进顺序建议：SCL → LAD/FBD（翻译器已存在）→ GRAPH / STL（先明确报不支持，再评估）。

**答复**：
SCL, LAD/FBD 以及存在，其他暂不支持。

### A13 · 图谱的关系边从哪来：自己解析 XML，还是取 TIA 的交叉引用？

**为什么要问**：图谱的价值一半在**边**（谁调用谁、谁用了哪个类型、谁引用了这个变量）。
Openness 其实**直接提供**权威答案：`CrossReferenceService` 能给出 unused / using / used-by
（见随包 skill `skills/change-detection/SKILL.md` 与 `skills/blocks/SKILL.md`）。
但它是**开项目**才有的能力，与"图谱层可离线、纯文本"的定位冲突。

**候选**
- A. **只解析 XML**（离线、快、与 TIA 解耦；但"引用"要靠推断，可能漏或错）
- B. **只取交叉引用**（权威；但必须开项目，图谱层不再能离线跑，CI 也难）
- C. **以 XML 解析为准，交叉引用作为校验/补充**（在线时对账，离线也能工作；成本最高）
- D. **分层**：结构性关系（组层级、类型引用）自己解析，**语义引用**（变量读写、used-by）取交叉引用

**倾向**：D。理由：结构关系在 XML 里是确定的，而"谁在哪个网络里读写了这个变量"
由 TIA 计算才可靠 —— 但这会让图谱的能力**按在线/离线分档**，需要你确认这个取舍。

**建议答复（草案 · 由 mcp-knowledge 的实测结论起草，待你确认或改写）**：

**这条与你的倾向 D 冲突，所以单独说明。** 参考实现选的是**候选 A：只解析 XML、不碰 TIA 交叉引用**。
值得强调的是它并非"靠推断"——最难的语义引用是从 XML 里**直接读出来**的：

- 边类型齐全：`CONTAINS`（组层级、块↔网段）、`CALLS`（含未导出被调方的**占位节点**）、
  `READS` / `WRITES`、`HAS_TYPE`、`INSTANCE_OF`、`CONNECTED_TO`（标签↔I/O 地址）、
  `EXECUTES_BEFORE` / `EXECUTES_AFTER`（网段执行序）、`REFERS_TO`。
- **"谁在哪个网络里读写了这个变量"** = FlgNet 的访问点 + 调用点 → `READS`/`WRITES` 边，
  并额外物化成 `knowledge_network_accesses` 表，让一次 JOIN 就能取全（`SemanticPlcGraph.cs`
  的 `RebuildDerivedData`）。这是**解析出来的**，不是 TIA 算出来的。

**选 A 的实际好处**：图谱层保持"纯文本解析、离线可跑"，正好满足 roadmap §4 的两条验收口径 ——
"**离线可 CI**：不依赖 TIA 即可跑通全部测试"与"拿真实导出物当 fixture 离线开发与测试"。

**代价（必须承认）**：跨块、跨 UDT 的深层引用闭包（unused / used-by 的完整集合）靠 XML 推断，
**可能漏或错**；`CrossReferenceService` 是权威答案而我们不用它。

**建议的落地口径**：**先按 A 起步**（离线、可 CI、已实测），把 D 里的交叉引用降级为
**后续的在线对账增强** —— 即"在线时用 `CrossReferenceService` 校验 XML 推断出的边，把差异报出来"，
而**不是**让它成为边的主来源。这样 A13 不再阻塞开工，也不必让整个图谱层按在线/离线分档。

**答复**：
A，纯XML解析，离线可用。

### A17 · 工具面：长操作（导出/编译）怎么表示？

**为什么要问**：导出 1151 块要 81.7 s，大项目编译"常需 10 分钟以上"，而默认 `requestTimeoutMs`
是 5 分钟、**超时即终止控制器并丢失会话**。现在的工具在这段时间里**完全不说话**（progress 帧有，

**候选**
- A. **阶段摘要**：把 progress 聚合成"已导出 340/1151"，随结果返回耗时与阶段

**倾向**：**先 A + C**（都不改变工具语义），确认框架能力后再考虑 B。

- **身份不确定的对象**（改名等）落进 `kind: rename-candidate` 等人工确认 ——
  这正是身份键缺口（A7 / 发行版 D7）的落点。

### B9 · "合适的时候"由谁判断？

模型自己判断、插件自动触发、还是用户显式询问。

**答复**（2026-10-14，取的保守默认，可调）：

- **默认：模型显式调用 + 用户可显式要求；插件不自动推送。**
  "何时调用"写进工具 description 与随包 skill（D4 三问的第一问），由模型判断；
  用户也可以直接问"有哪些变更"。
- **为什么不自动注入常驻上下文**：上下文经济（[`vision.md`](vision.md) §4 第 4 条）——
  变更台账会随项目规模增长，常驻化等于让每个会话都付一份与它无关的账；
  而且"合适的时候"若由插件猜，猜错就是把无关信息塞进上下文。
- **可调**：将来若证明"会话开头带一句变更摘要"确实有用，改成
  "首轮注入一行固定上限的摘要 + 细节仍按需下钻"即可，**不影响数据模型**。

### B16 · 图谱能力的暴露形态？

新增工具族、随包出货的工程索引文件，还是注册成 skill 资源。

**建议答复（草案 · 由 mcp-knowledge 的结论 + 本仓实测成本起草，待你确认或改写）**：

**三种都用，但分工明确：工具族分两层，知识走 skill。** 直接照搬参考实现的 16 个工具不可行 ——
接口插件族的 26 个工具实测已占 **50,593 字符**常驻（`tool-surface.md:352-354`），而参考实现 16 个工具里
**有 6 个是图浏览器**（`query_node_kinds` / `query_nodes` / `query_edge_types` / `query_edges` /
`query_node_properties` / `query_edge_properties`）。原样搬进来会让每个会话付约 8 万字符，
既与 `architecture.md` §6「上下文经济」冲突，也与 roadmap §2 第 6 项（26 个 → 少量工作流工具）
和 `tool-surface.md` §6.2 的收口方向相反。

| 层 | 内容 | 默认 |
|---|---|---|
| **工作流工具（6–8 个）** | `plc_knowledge_status`、`plc_knowledge_ingest`、`plc_knowledge_update`、`plc_get_block`、`plc_get_network`（把"取单个网段"与"分块取逻辑"用 offset 合一）、`plc_variable_usage`、`plc_search` | **暴露** |
| **原子层** | `query`（任意只读 SQL）+ 上面 6 个图浏览器 | **不暴露**，走配置开关；对齐 A15 的"保留但默认不暴露" |
| **skill（bundled）** | SQLite schema 词表（节点种类 / 边类型 / 12 条示例查询）+ 节点边语义 + 使用策略 | 按需加载，不占常驻 |

**`get_schema` 这个工具不要单独保留**：它返回的是**静态** DDL + 词表，正是 skill 的形态
（对照接口插件族的 `skills.ts` 路由 skill 与 D4）。参考实现为它加的"版本哈希 → `unchanged:true`"
优化，是因为 MCP 侧没有 skill 机制；本仓有，这个技巧可以省掉。

**答复**：
回答特定工程问题的agent会启用子agent，其中会隐藏一些操作层面的工具。但是图谱方面的工具是需要暴露给子agent的。所以先把工具暴露出来。skill不好，可能不是按需，最新。
