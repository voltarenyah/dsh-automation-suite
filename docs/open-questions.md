### A8 · 上下文族：git 底层能力怎么引入？

**为什么要问**：你提到"其中可能又需要引入 git 的底层能力"。仓库里已有一族结构化 git 工具（12 个），
但它面向的是普通仓库操作，不一定够用。

**候选**
- A. **复用** `packages/dsh-tool-git` 的现有工具（零新依赖，但它的抽象层次是"给人用的 git"）
- B. 引入 git 库（如 isomorphic-git / nodegit / libgit2 绑定）做程序化操作（能力强，多一个重量级依赖）
- C. 直接调 `git` 命令（`execFile`，与现有插件的 shell-free 风格一致）

**同时需要你判断**："底层能力"具体要哪些原子操作？例如：历史遍历、树/blob 读取、
工作副本物化到指定版本、两版之间的对象级差异、局部提交。

**倾向**：C 起步（与现有 `execFile` + 参数数组的安全风格一致，无新依赖），
只有出现性能或并发瓶颈时才考虑 B；A 作为面向模型的上层工具保留。

**答复**：
我无法现在直接给你答案。但是我有几个问题。
引入git库对于dsh发行版来说是常规操作吗？它还是以插件的形式存在的吗？
因为这个底层git能力并非直接暴露给用户的，而是被工程上下文插件调用实现功能的。
另外直接让agent调git命令是否会存在不确定性，比如路径搞错了，参数忘记带等等，如果希望一致性好的话，是不是还是要用插件对git做二次封装只暴露工具更好。

**补充分析（供决策，来自本仓约定与已实现代码）**：

- **引入第三方库是常规操作**：DSH 插件就是普通 Node 包，可以在 `dependencies` 里声明任何 npm 依赖，
  由 profile 安装时落进它的 `node_modules`。本仓唯一的限制是**不许把 `@deepseek-ai/*`（宿主运行时）
  声明为依赖**（见根 `AGENTS.md` §3）—— 第三方库不在这个禁令里。
- **它不必是插件**：`packages/` 下的包目前都带 `dsh.bundle.patch`（= 插件），但没有这个字段的包
  就是**普通库**，作为别的插件的依赖存在。所以要"只给上下文插件内部调用、不暴露给用户"，
  有两条路：① 直接写进上下文插件包内部；② 单独出一个**库包**（无 patch）供它依赖，便于测试与复用。
- **"让 agent 调 git 命令"和"插件内部调 git"是两件事**，你担心的不确定性只属于前者：
  - **插件内部调用**：参数在**代码里**拼好（`execFile('git', [明确参数])`），
    路径来自插件自己解析的 workspace，模型不参与 —— 没有"忘带参数"的空间；
  - **模型直接指挥 git**：路径与参数由模型生成，才会出现你担心的错漏。
  本仓 `dsh-tool-git` 已经用 `execFile` + 显式参数数组做到了"无 shell 注入、无字符串拼接"，
  是一个可以直接照抄的先例。
- **你的结论我认同并且已经写进架构**：**不要**把原始 git 能力暴露给模型，而是由插件做二次封装、
  只暴露**工程域**的工具（例如"这个版本相对上一版，哪些块变了"），
  这与"写入只有一个通道"是同一个思路。现有那 12 个面向模型的 git 工具是**通用**能力，
  与 PLC 工程无关；上下文插件**不应依赖模型去调它**，而应自己调 git。
